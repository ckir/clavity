**Disposition (FINAL, after the follow-up measurement below): no legacy plugin lingers in any way that
reaches an upgrading user, so Task 6.3 was correctly skipped.** The two commands specified by the plan

**Disposition from the two specified commands alone: cannot determine; tracked.**

The first command's fallback (`"no cached legacy clavity plugin present"`) did not fire — the glob matched five directories. But the glob `*clavity*` is not a legacy-vs-current filter: it also matches unrelated current products (`clavity-agy-autotrain`, `clavity-commonmemory`, `clavity-commonmemory-dev`, `clavity-ns-spike`) and the `clavity-dotnet` product's own cache folder name, none of which by themselves indicate a *legacy-named plugin* is present — the command as specified cannot distinguish "a directory whose name happens to contain the string clavity" from "a plugin still installed/loaded under its pre-rename `name` field." Settling that requires inspecting what's inside the matched directories and cross-referencing `~/.claude/plugins/installed_plugins.json`, which is investigation beyond what this command's output alone shows, and beyond the scope of this one-pass, non-adversarial transcript. The second command found no `LegacyPluginName` implementation anywhere in the repo, which is consistent with either disposition (skipped because unneeded, or skipped because never resolved) and does not itself settle the question.

What would settle it: an explicit definition of what Task 6.3 means by "legacy plugin lingering" — active/installed-only (checked via `installed_plugins.json`) versus any on-disk residue (checked via cache contents) — plus, if active/installed is the relevant criterion, confirmation of whether the plugin's pre-rename name (`clavity-dotnet` / `clavity-classic` as a plugin `name` field, not a folder name) was ever shipped to real end users before the rename landed. Neither this transcript's method nor its two commands resolve that.

## Step 7b — follow-up measurement that settled Spike B

The plan's two commands could not answer the question, so the question was answered directly. Nothing
below modifies any epic artifact; it is measurement plus one throwaway probe run outside the repo.

**(1) The rename has never shipped.** Plugin `name` at every release tag:

```
$ for t in $(git tag --sort=-creatordate | head -6); do ... git show $t:clavity-dotnet/plugin/plugin.json | jq -r .name ...; done
clavity-v13  2026-07-24  name=clavity-dotnet  ver=0.3.1
clavity-v12  2026-07-21  name=clavity-dotnet  ver=0.3.0
clavity-v11  2026-07-20  name=clavity-dotnet  ver=0.3.0
clavity-v10  2026-07-13  name=clavity-dotnet  ver=0.2.1
clavity-v9   2026-07-13  name=clavity-dotnet  ver=0.2.0
clavity-v8   2026-07-12  name=clavity-dotnet  ver=0.1.15
```

So every existing end user holds `enabledPlugins["clavity-dotnet@clavity-dotnet"] = true`.

**(2) The MARKETPLACE name did NOT change across the rename — only the plugin name did.**

```
$ jq -r '.members[]|select(.name=="clavity-dotnet")|"pluginName=\(.pluginName // "(absent)") marketplaceName=\(.marketplaceName)"' build/members.json
HEAD: pluginName=clavity        marketplaceName=clavity-dotnet
v13:  pluginName=(absent)       marketplaceName=clavity-dotnet
```

This is the load-bearing fact. `installer/_shared/register-plugin.ps1:130` removes `$MarketplaceName`
— which is `clavity-dotnet`, i.e. *the same marketplace the legacy plugin is registered under*.

**(3) `marketplace remove` cascades to `enabledPlugins`.** Measured by probe, not assumed. A throwaway
marketplace `zzprobe-mkt` / plugin `zzprobe-plugin` was added from a scratch directory outside the repo,
installed, then its marketplace removed; `~/.claude/settings.json` was snapshotted first and verified
semantically identical afterwards.

```
after install:  enabledPlugins has zzprobe-plugin@zzprobe-mkt = true   (13 -> 14 keys)
after marketplace remove:  key absent                                   (14 -> 13 keys)
diff <(jq -S . settings.json.PREPROBE) <(jq -S . ~/.claude/settings.json)  ->  no differences
```

The probe also showed the cache DIRECTORY survives, stamped with a `.orphaned_at` marker.

**(4) The transition is already recorded on this machine.** The legacy-named cache entries carry exactly
that marker, one per historical version, while the renamed plugin does not:

```
~/.claude/plugins/cache/clavity-dotnet/clavity-dotnet/0.2.1/.orphaned_at -> 1784608149273
~/.claude/plugins/cache/clavity-dotnet/clavity-dotnet/0.3.0/.orphaned_at -> 1784876091066
~/.claude/plugins/cache/clavity-dotnet/clavity-dotnet/0.3.1/.orphaned_at -> 1784915585490
~/.claude/plugins/cache/clavity-dotnet/clavity/0.3.1/            (live, no marker)
```

**Conclusion.** A v13 user upgrading runs `marketplace remove clavity-dotnet` (`register-plugin.ps1:130`),
which cascades their stale `clavity-dotnet@clavity-dotnet` key away, before `plugin install
clavity@clavity-dotnet` (:134) enables the renamed plugin. The legacy cache directory is left on disk but
orphaned and not loaded. There is therefore no double-fire and no need for `LegacyPluginName` clean-break
logic: **SP-0 Task 6.3 was correctly skipped.**

**The assumption this now rests on, stated so it can be re-verified rather than trusted:** that
`claude plugin marketplace remove` cascades to `enabledPlugins` is HOST behaviour we do not own and do not
control. It was true when measured (see the probe above). If Claude Code ever stops cascading, the
conclusion here flips and `LegacyPluginName` becomes necessary. Re-run the probe rather than re-reading
this paragraph — a recorded result is evidence about the day it was taken, not a standing guarantee.
